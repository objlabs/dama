# Dama 설계 초안

## 목표와 사용자

자신의 서버에서 여러 프로젝트를 운영하는 개인 개발자와 소규모 팀이 첫 대상이다. 기존 Nginx(+SSL) → Docker 운영 구조를 활용한다. 앱과 직접 배포한 MCP, 외부 MCP를 한 공간에서 관리하고, 향후 에이전트가 이 운영 데이터를 읽고 승인된 작업을 수행하도록 한다.

첫 배포 대상은 Linux 서버 한 대이다. 개발 대시보드는 macOS에서도 실행한다. 다중 테넌트 호스팅, Kubernetes, 글로벌 엣지와 임의 사용자 코드 실행은 초기 범위에 포함하지 않는다.

## 구성

```text
브라우저 대시보드
    │ 동일 출처 관리 API
    ▼
Control plane ── SQLite / 변경 기록 / 비밀 참조
    ├─ 프로젝트 레지스트리
    ├─ MCP 레지스트리와 사용 연결
    ├─ [후속] 빌드·배포 작업 큐 → 서버 실행 에이전트
    │                         ├─ 격리된 빌드 환경
    │                         ├─ Docker 앱 컨테이너
    │                         └─ Nginx / 인증서 관리자
    └─ [후속] 운영 AI → 권한 검사 / 승인 / 도구 실행
                              ├─ 내부 운영 도구
                              └─ 등록된 외부·직접 배포 MCP
```

현재 구현은 대시보드, 관리 API, 레지스트리, 프로젝트별 MCP 사용 연결, 변경 기록이다. 운영 API를 훗날 MCP로 노출할 수 있지만 MCP가 내부 API를 대체할 필요는 없다.

TypeScript strict 모드로 서버·브라우저·테스트를 작성하고 공통 데이터 타입을 공유한다. Node.js의 내장 HTTP 서버와 SQLite를 사용하며 실행 시 외부 런타임 의존성은 없다. TypeScript와 Node 타입 정의는 개발 의존성이다. 서버/브라우저를 별도 tsconfig로 컴파일하고 정적 자산과 실행 코드는 dist/에 배치한다. 초기 DB 요청은 짧은 동기 작업이다. 빌드·도구 실행은 요청 처리에서 분리한 워커로 구현한다. 장시간 작업이나 동시 사용이 커지면 비동기 저장 계층 및 큐로 전환한다.

## 현재 데이터 모델

모노레포 확장과 v2 마이그레이션의 상세는 [서비스 설계](monorepo.md)를 따른다. Project는 저장소 그룹, Service는 Docker 배포 단위다. 기존 Project.kind는 v1 MCP 참조 호환을 위해 유지한다.

- **Service**: 프로젝트 참조, 이름, 유형, 언어, 소스 경로, Dockerfile, 빌드 컨텍스트, 내부 포트, 접속 경로, 상태 확인 경로, 변경 감지 경로, 등록·수정 시각.

- **Project**: id, 이름, 유형(app/mcp), 저장소 URL, 브랜치, 도메인, 등록 시각.
- **McpServer**: id, 이름, 출처(external/managed), transport, endpoint, 제공 Project 참조, credentialRef, 등록 시각.
- **Binding**: id, 사용하는 Project 참조, McpServer 참조, 예정 실행 정책, 등록 시각. 동일 프로젝트·MCP 조합은 하나만 등록한다.
- **Event**: 작업 종류, 대상 id, 표시 이름, 시각. 현재는 관리 데이터 변경 이력이며 위변조 방지 감사 시스템은 아니다.

Project가 MCP를 **제공하는 관계**와 Project가 MCP를 **사용하는 관계**는 다르다. managed MCP의 제공 프로젝트는 반드시 kind=mcp여야 한다. 외부 MCP는 배포 프로젝트를 갖지 않는다. 현재 등록·연결·삭제와 이벤트 기록은 단일 트랜잭션으로 저장한다.

- **BuildJob**: 서비스 ID, 전체 커밋 SHA, 등록 시점의 소스와 Docker 빌드 설정, 등록 시각. SQLite에 대기 작업을 보관하며 수동 등록과 취소를 지원한다.

후속 모델: Server, Deployment, Domain/Certificate, Credential, Agent, AgentBinding, ToolPolicy, Approval, ToolInvocation, Metric. 인증 정보는 레지스트리와 분리하며 전역 인증 참조와 프로젝트별 계정 덮어쓰기를 지원한다. 환경별 설정 및 도구별 허용 목록을 추가한다. 현재 `user_version=4`이며 기존 프로젝트와 서비스를 보존하는 마이그레이션을 지원한다.

## MCP 관리

첫 구현은 Streamable HTTP 메타데이터를 지원한다. stdio MCP는 프로세스 실행, 파일 접근, 환경변수와 수명주기 관리가 필요하므로 별도 격리 실행기로 확장한다.

MCP를 등록했다고 연결되거나 도구를 실행할 수 있는 것은 아니다. 후속 단계에서 initialize 협상, 지원 프로토콜 버전, tools/list 등 제공 기능 탐색과 연결 테스트를 구현한다. 프로세스 정상, HTTP 응답 정상, MCP 협상 성공을 별도 상태로 기록한다.

외부 연결 단계에는 타임아웃, 응답 크기 제한, 리다이렉트 정책과 DNS 재검증을 둔다. 자기 서버의 내부 MCP도 사용해야 하므로 내부망 주소는 무조건 금지하는 대신 관리자가 허용한 네트워크에 한해 허용한다. 클라우드 메타데이터 주소는 차단한다. 현재는 서버가 등록 URL을 호출하지 않는다.

초기에는 레지스트리와 프로젝트별 연결을 제공한다. 모든 MCP를 하나의 엔드포인트로 합치는 게이트웨이는 후속 기능이다. 게이트웨이는 사용자별 인증·도구 이름 충돌·세션·스트리밍·호출 제한·감사 기록까지 처리해야 한다. HTTP URL만 등록한다고 GPT·Claude 제품에 자동으로 연결되는 것은 아니며 각 클라이언트의 연결 지원을 확인한다.

## 배포 수명주기 — 후속 구현

기본 주소는 `https://apps.objlabs.team/<프로젝트 UUID>/`로 확정했다. 기본 호스트의 개별 인증서와 ACME HTTP-01 검증을 사용한다. 기존 서버는 와일드카드 인증서 경로를 지정해 재사용하고, 신규 Linux 설치는 Certbot, Windows 기존 환경은 win-acme를 활용할 수 있다. UUID 경로는 업스트림에 보존하며 앱의 base path 지원이 필요하다. 구현된 주소 생성 및 Nginx 설정 출력과 운영 절차는 [도메인·HTTPS 운영](domains-and-tls.md)을 따른다. 커밋을 직접 등록하면 배포 워커가 빌드부터 Nginx 전환까지 처리한다. 인증서 발급과 갱신은 기존 ACME 도구에서 관리한다.

1. GitHub App 또는 저장소 웹훅을 수신하고 서명·이벤트 id를 검증한다. GitHub Actions에 의존하지 않는다.
2. 저장소·브랜치 규칙을 확인하고 정확한 커밋 SHA로 배포 작업을 생성한다. 중복 이벤트를 제거한다.
3. 운영 컨테이너와 분리된 환경에서 리소스·시간을 제한하여 빌드하고 고유 이미지 digest를 기록한다. 저장소 코드와 빌드 스크립트는 신뢰하지 않는다.
4. 프로젝트 단위 잠금으로 동시 배포를 직렬화한다. 새 컨테이너를 고유 내부 주소로 실행한다.
5. 상태 확인 경로, 타임아웃, 재시도 조건으로 준비 상태를 검증한다.
6. Dama 소유의 Nginx include 설정을 생성하고 `nginx -t`로 검증한다. 기존 설정을 보존하고 원자적으로 전환한 뒤 reload한다.
7. 전환 후 실제 경로 확인에 실패하면 이전 설정으로 복원·검증·reload한다. 복구도 실패하면 추가 변경을 멈추고 운영자에게 알린다.
8. 연결 종료 유예 후 기존 컨테이너를 정리한다. 롤백용 이미지와 배포 설정은 보관 정책에 따라 남긴다.

### 빌드 동시성

빌드 서버마다 동시 빌드 작업 수를 설정한다. 기본값은 1이며, 운영자가 한도를 높이면 빌드 의존성이 없는 서비스 작업을 동시에 실행할 수 있다. 다른 작업의 산출물이 필요한 경우에는 명시한 선행 빌드가 성공한 뒤 실행한다. 선행 빌드가 실패하면 해당 산출물을 사용하는 작업은 실행을 보류한다.

동시 빌드 한도는 큐에서 꺼낸 서비스 작업 수에 적용한다. 한 작업 내부의 스테이지나 컴파일러 병렬 실행은 빌더 설정에 따르며, 워커 전체 CPU·메모리 예산은 별도로 적용한다. 빌드가 병렬로 완료되어도 프로젝트별 배포 잠금을 적용하고, DB 마이그레이션 작업은 같은 대상 DB에서 하나씩 실행한다.

트래픽 롤백은 DB 스키마나 볼륨 데이터를 복원하지 않는다. 배포와 호환되는 DB 마이그레이션, 백업 및 복원 절차를 따로 둔다. SSL은 ACME 발급·갱신·만료 알림·실패 재시도 및 challenge 라우팅을 포함한다.

## 기존 환경 가져오기

처음에는 Docker/Nginx 정보를 읽기 전용으로 조회한다. 컨테이너·볼륨·네트워크·설정 파일을 표시하고 관리 대상으로 명시적으로 선택하게 한다. Dama가 소유하지 않는 컨테이너나 설정을 자동 삭제하지 않는다. Docker socket을 관리 웹 프로세스에 직접 노출하지 않고 좁은 명령 API를 제공하는 실행 에이전트를 둔다. 실행 에이전트는 강한 권한을 갖기 때문에 별도 인증과 명령 허용 목록이 필요하다.

## AI 운영

모델 제공자와 에이전트 실행기는 별개로 취급한다. 로컬 모델, GPT 및 Claude API 연결은 교체 가능한 어댑터로 둔다. 도구 호출을 지원하는 모델·클라이언트의 기능 차이를 확인한다.

AI의 첫 역할은 읽기 전용 분석이다. 앱별 배포 이력, 로그, 메트릭과 탐지 도구의 결과를 읽고 근거를 붙여 설명한다. 취약점 판단은 스캐너·정책 검사의 실제 결과를 사용한다. 로그와 MCP 응답은 신뢰할 수 없는 데이터이며 지시로 실행하지 않는다. 외부 모델 전송 전 마스킹과 전송 범위 설정을 적용한다.

수정 작업은 도구별 허용 정책과 유효 기간이 있는 구체적 승인을 통과해야 한다. 승인 대상에는 도구·프로젝트·정확한 인수와 상태 버전을 포함하고 실행 시 재검증한다. 모델이 직접 권한을 부여하지 못한다. 결과와 실패도 기록한다. 현재 read-only/approval-required는 저장된 의도일 뿐 실행 권한 체계가 아니다.

## 인증과 운영 경계

현재는 단일 로컬 사용자용 개발 도구이다. 루프백 수신, Host/Origin 검사, CSP, 입력 검증, body 크기 제한을 사용한다. 실제 토큰은 저장하지 않는다. 외부 공개 전 소유자 인증·세션·CSRF·호출 제한·비밀 암호화·복구 키·백업/복원·TLS 설정이 필요하다.

SQLite 파일과 인증 저장소는 앱 데이터 볼륨으로 분리한다. 백업은 동작 중 DB를 단순 복사하기보다 SQLite 백업 API나 정상 중지 후 일관된 스냅샷을 사용한다. 초기 릴리스 전에 라이선스, 기여 규칙, 보안 제보 절차와 지원 범위를 결정한다.
